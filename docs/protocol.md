# Контракт инструментов

MCP-сервер работает по `stdio`. Все инструменты возвращают JSON-объект с `ok`. Ошибка возвращается как `{"ok": false, "error": {"code": "...", "message": "..."}}`. Клиент не должен трактовать доставленный ответ MCP как успешную проверку: он должен прочитать `ok` и результат оценки.

## Регистрация

`register_task(name, question, database_path, reference_sql, tags=[], ordered=false)` создаёт локальный снимок SQLite-файла. Путь указывается относительно каталога `--data-root`. Эталон должен быть проверен по смыслу вопроса до регистрации. Для результата с существенным порядком укажите `ordered=true`; по умолчанию используется сравнение мультимножеств, сохраняющее повторяющиеся строки.

В ответе содержится `task_id`, который используется в дальнейших вызовах. Исходная база не предназначена для изменений этими инструментами.

## Варианты

`add_variant(task_id, name, operations, partition="practice")` создаёт отдельный вариант исходного снимка. `partition` принимает `practice` или `holdout`. После первой оценки задачи варианты заморожены.

Каждая операция содержит `kind`, `table` и параметры:

```json
{
  "kind": "insert",
  "table": "orders",
  "values": {"id": 3, "customer": null, "amount": 20}
}
```

```json
{
  "kind": "update",
  "table": "orders",
  "values": {"amount": 0},
  "where": {"id": 2}
}
```

```json
{
  "kind": "delete",
  "table": "orders",
  "where": {"id": 2}
}
```

Условия `where` соединяются через AND и сравниваются на равенство; `null` означает `IS NULL`. Для `update` и `delete` пустое условие запрещено. Список операций применяется к копии атомарно: неудачная операция не должна оставлять частичный вариант.

Сервер проверяет исполнимость и ограничения базы. Правдоподобие изменения по бизнес-правилам должен проверить агент. Сценарий с отрицательной суммой, например, пригоден только когда постановка разрешает корректировки или возвраты.

## Оценка

`evaluate(task_id, candidate_sql, partition="practice")` возвращает `attempt_id` и результаты сравнения. `practice` проверяет исходный снимок и практические варианты; `holdout` — только отложенные варианты. Содержимое строк ответа не передаётся клиенту.

SQL исполняется как операция чтения с ограничениями SQLite и бюджетами выполнения. Неполная выборка, запрещённая операция или превышение лимита не должны интерпретироваться как совпадение с эталоном. Число совпадений описывает только пройденные состояния, а не вероятность правильности запроса на неизвестных данных.

## Память

`propose_lesson(task_id, failing_attempt_id, passing_attempt_id, title, rule, tags=[])` создаёт кандидат в правило. Неудачная попытка должна показать семантическое различие, успешная — пройти практические случаи. Ошибка исполнения не заменяет доказательство семантического различия.

`activate_lesson(lesson_id)` проверяет последние практическое и отложенное выполнения того же исправленного SQL для этой задачи: оба должны быть успешными. Неудачная попытка должна предшествовать исправлению. Для активации нужны хотя бы один практический и один отложенный вариант. Политика намеренно консервативна: обычная успешная задача без выявленной ошибки не создаёт урок исправления.

`retrieve_lessons(tags=[], limit=5)` возвращает только активные правила. `retire_lesson(lesson_id)` исключает правило из активной выдачи. `get_task(task_id)` возвращает состояние задачи.

Наличие идентификаторов и прохождение проверок не валидирует свободный текст правила. Его семантика и область применимости требуют отдельного суждения. В первой версии такой проверки независимой моделью нет.
